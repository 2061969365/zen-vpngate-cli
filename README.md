# VPNGate + sing-box + OpenCode 官方 CLI 多节点实测方案与结论

本项目用于验证 OpenCode 免费模型（`deepseek-v4.1-flash-free`）在不同出口 IP 下的可用性，对比官方 CLI 与各类网关的 429 报错行为，并测试基于 VPNGate + sing-box 的动态出口池方案。

---

## 一、核心结论

1. **429 是出口 IP / ASN 维度的配额与风控，绝非全局共享池耗尽**
   - **GitHub Actions 直连（Azure AS8075）**：所有 runner 出口 IP 均被秒级拒绝 429，`Retry-After: ~79200`（指向次日 UTC 00:00）。
   - **自建单 IP 代理**：在消耗完几轮对话后也会进入 429。
   - **VPNGate 节点池**：在同一时间（同一 UTC 配额周期）内，**86 个节点中有 13 个节点成功通过官方 CLI 完成真实多轮对话并稳定返回 200**！这确凿推翻了“上游免费层全局耗尽”的假设。

2. **VPNGate 全量 TCP 节点池体检数据（86 个独立节点测试）**

| 状态分类 | 数量 | 占比 | 实际现象与技术归因 |
|---|---|---|---|
| **OK200（真正可用）** | **13** | **15.1%** | 官方 CLI 真实生成内容，无 429，多轮会话正常 |
| **429（已耗尽/被限）** | **12** | **14.0%** | 隧道通且能连 opencode，但该公共出口 IP 的免费额度已被刷满 |
| **ECONNREFUSED（被上游拒连）** | **38** | **44.2%** | 隧道能正常出网（ipify 200），但连接 `opencode.ai:443` 时被直接拒连/RST |
| **NO_EGRESS（隧道未建立）** | **22** | **25.6%** | OpenVPN 握手超时、服务端掉线或无外网出口 |
| **ECONNRESET** | **1** | **1.1%** | 握手中途被中断 |

> **出网连通节点总数**：$13 + 12 + 38 + 1 = 64$ 个（占 74.4%），与预期的 60~70 个连通节点完全吻合。其中能成功请求到 AI 模型的纯净可用出口为 13 个。

## 二、架构与关键代码优化

1. **转换器集成**：使用 `railway-vpngate-combined` 中的 `vpngate_to_singbox.py`，将 VPNGate OpenVPN TCP 节点转换为 sing-box 1.14+ 原生 `openvpn-client` 协议配置。
2. **避免假就绪 Trap**：sing-box 的 mixed 入站端口一旦启动便立刻 listen，哪怕底层 VPN 尚未连通。因此在 `tests/run_nodes.py` 中重构为：
   - 监听端口就绪后，以 2 秒间隔轮询探测 `https://api.ipify.org`，直到真正拿到 HTTP 200 才判定隧道畅通。
   - 最大探测超时 50 秒，失败自动判定 `NO_EGRESS`。
3. **高并发并行执行器**：
   - 6 个 Shard 按取模跨越分片分配节点（`i % TOTAL_SHARDS == SHARD - 1`）。
   - 每个 Shard 内部采用 `concurrent.futures.ThreadPoolExecutor(10)`，10 并发启动独立 sing-box 进程和随机端口。
   - 仅对出网正常的节点派发官方 `opencode run`，单 Shard 14~15 节点耗时控制在 90~140 秒内。
